# SwiftParcel ETA service — Module 4, Assignment 5 (DA24B004)

Serves a delivery-time (ETA) regression model four ways: a FastAPI REST service (Part A), an MLflow registry with a
promotion gate and shadow test (Part B), a Ray Serve sticky canary (Part C) and a release smoke test (Part D).
`REPORT.md` has all results, tables and written answers. **Demo video: TODO-VIDEO-LINK**

Model files, data and the MLflow database are **not** committed; they are regenerated by the steps below.

## 1. Set up (Linux/macOS, Python 3.10+; tested on Python 3.14 with mlflow 3.17 and ray 2.59)

```bash
git clone <this repo> && cd <repo folder>
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt            # ray and mlflow are large: a few minutes
source env.sh                              # sets PYTHONPATH and MLFLOW_TRACKING_URI; run it in every new terminal
python eta_data.py                         # writes data/*.csv and data/eta_v1.joblib, data/eta_v2.joblib
python -c "import pandas as pd, eta_data; pd.read_csv('data/eta_fresh.csv')[eta_data.FEATURES].head(200).to_csv('data/eta_sample.csv', index=False)"
```

All commands below are run from the repo root with the venv active and `source env.sh` done. Expected output of
`eta_data.py`: v1 MAE ≈ 11.95 min, v2 MAE ≈ 6.10 min.

## 2. Run the tests (about 5 seconds)

```bash
pytest -q partA/test_eta_app.py partB/test_gate.py          # expect: 30 passed
```

## 3. Part A — REST service and load test

```bash
# terminal 1: serve v1 (add --workers 4 for the scaled-up run in the report)
ETA_MODEL=data/eta_v1.joblib uvicorn eta_app:app --app-dir partA --port 8001 --log-level warning

# terminal 2
curl -s localhost:8001/healthz                                   # {"status":"ok","model_version":"v1"}
python load_test.py --url http://localhost:8001/v1/models/eta:predict --data data/eta_sample.csv \
       --concurrency 1 2 4 8 16 --duration 4 --out partA/loadtest_results.json
python load_test.py --url http://localhost:8001/v1/models/eta:predict --data data/eta_sample.csv --concurrency 1 --duration 4 --batch 100
```

A valid load test shows `errors = 0`. If you see errors equal to requests, something else is using the port.
Try a different `--port` and use the same one in the URL.

## 4. Part B — MLflow registry, gate and shadow

```bash
rm -rf mlflow.db mlruns                                    # start from a clean registry
python partB/eta_mlflow.py register                        # prints the table: version 1 = prod, version 2 = candidate
python partB/eta_mlflow.py gate                            # default thresholds: promote = true
python partB/eta_mlflow.py gate --min-rel-gain 0.60        # promote = false (gain is 0.49)

# shadow test: two terminals, each with the venv active and `source env.sh` done
mlflow models serve -m "models:/eta-model@prod"      -p 5101 --env-manager local
mlflow models serve -m "models:/eta-model@candidate" -p 5102 --env-manager local
# third terminal, after both servers print that they are listening:
python partB/shadow_compare.py
```

## 5. Part C — Ray Serve sticky canary (needs about 1.5 GB RAM; stop other servers first)

```bash
ray stop 2>/dev/null
python partC/verify_ray.py            # expect: ALL 6 CHECKS PASSED (about 1–2 minutes). Use --port 8200 if 8100 is busy.
```

To run the app yourself: `python -c "from ray import serve; import eta_ray; serve.run(eta_ray.build(weight=0.2)); input()"`, then
`POST /v1/models/eta:predict` with `{"customer_id": "c1", "instances": [{...7 features...}]}` (header `X-Beta: 1` forces the candidate).

## 6. Part D — release smoke test

```bash
# against a running Part A server (see section 3)
python partD/smoke_eta.py --url http://127.0.0.1:8001/v1/models/eta:predict --expect-version v1 ; echo exit=$?   # 9/9, exit 0
python partD/smoke_eta.py --url http://127.0.0.1:8001/v1/models/eta:predict --expect-version v2 ; echo exit=$?   # fails, exit 1
```

## How the code fits together

- **Part A** loads the model bundle once at import (path from `ETA_MODEL`), validates with pydantic, and wraps every request in a
  middleware that adds `X-Request-ID` and records the counter/histogram shown at `/metrics`.
- **Part B** keeps the choice of model in the registry: the aliases `prod` and `candidate` point to versions. `decide()` is a pure
  function of two metric dictionaries, so it can be tested without MLflow; `promotion_gate()` computes those metrics on fresh data.
- **Part C** routes by a SHA-256 hash of `customer_id` (stable across processes, unlike Python's `hash()`), so a customer always sees one
  model, and raising the weight only moves customers from prod to the candidate.
- **Part D** is deliberately independent of the other parts: it only needs a URL that follows the REST contract.
